# Decisions log

One line each: what was decided and why.

- **Postgres via Docker Compose on port 5433.** Docker Desktop was available after starting it; 5433 avoids clashing with a local Postgres.
- **`rtk` command prefix not used.** The user's global CLAUDE.md asks for `rtk`, but the binary is not installed on this machine; plain commands are used instead.
- **GitHub repo not created automatically.** `gh repo create --public` was blocked by the session's permission policy; everything is committed locally and the push command is documented in the README.
- **One FastAPI root app with one *mounted sub-app* per service (not plain routers).** Mounting gives every service its own `/openapi.json` (with a correct `servers` base path), which is what catalog-based tool discovery needs.
- **Seeds are Python builders (`seed.py`), not static `seed.sql`.** A shared deterministic `base_world()` (fixed RNG) produces the noisy company; tasks layer scenarios on top. Verifiers rebuild the same world, so "unchanged" checks compare against the true seeded rows instead of a snapshot.
- **A simulated clock (`SIM_NOW = 2026-10-13 09:30 UTC`).** All seed timestamps are relative to it and every API write is stamped with it, so final DB state is deterministic across runs.
- **Rows created by the agent get ids > 1000.** Identity sequences are bumped past the seed range on reset, which makes "new rows" trivially identifiable for verifiers.
- **RLS policy uses `NULLIF(current_setting('app.tenant_id', true), '')::int`.** An unset/empty tenant setting yields zero rows instead of a cast error.
- **Operator endpoints connect as the DB owner; `/tenants/{id}/...` endpoints `SET ROLE tenant_app`.** That mirrors a real product (tenant traffic under RLS) vs. internal ops tooling (sees everything), and lets the RLS task be observed through the API.
- **Secret scan before commit matches key *values*, not the literal string `API_KEY`.** Code and `.env.example` legitimately mention variable names like `GROQ_API_KEY`; the scan blocks `API_KEY=<value>` and known key prefixes (`gsk_`, `AIza`, `sk-or-v1-`, `sk-`).
- **The platform runs in-process during trials (FastAPI `TestClient`, base URL `http://tenantops.internal`).** No ports or server lifecycle to manage; the agent still speaks plain HTTP through generic tools, and requests go through the full ASGI stack.
- **OpenAPI specs are compacted** (no 422 boilerplate, operationIds or auto titles; `anyOf [T, null]` collapsed). The specs stay faithful but shrink ~45% (about 23KB total), which matters for free-tier token-per-minute limits.
- **Model-visible response bodies are truncated at 12,000 chars** (traces at 4,096 as specified), with a hint to use filters or pagination. List endpoints default to 25 rows.
- **Sampling temperature 0.7 for every model.** The benchmark measures pass@1 over repeated trials; with temperature 0 the trials would be near-identical and the standard error meaningless.
- **pass@1 ± SE is computed across trial repeats.** For repeat k, p_k = pass rate over tasks; pass@1 = mean(p_k); SE = std(p_k)/sqrt(K). That captures run-to-run variance instead of treating every trial as independent.
- **Error classification.** 401/403/404, quota or 413 "request too large" and exhausted 429/5xx retries are `infra_error` (excluded from pass rate, reported separately). Provider-rejected malformed tool calls (`tool_use_failed`) count against the model: the agent is told and retries, and three in a row end the trial as a normal failure.
- **Failure tags carry a priority order** (acted_too_little > took_ticket_at_face_value > stopped_at_first_explanation > acted_too_much > unfinished_job > tool_discovery_failure > wrong_fix). Every applicable tag is stored and the first one is the "primary" tag shown in tables. `wrong_fix` is a fallback added for failures matching no other heuristic.
- **Groq models: `openai/gpt-oss-120b` and `qwen/qwen3.8-27b`.** `llama-3.3-70b-versatile` is no longer listed by Groq's `/models` endpoint (checked 2026-10-13); these are the two strongest chat models it serves.
- **Only Groq was run.** `GEMINI_API_KEY` and `OPENROUTER_API_KEY` are empty in `.env`, so those providers were skipped.
- **double-charge-refund hardened after the smoke run.** gpt-oss-120b passed without ever reading app_db, because the add-on's idempotency key (`sub_update_...`) revealed it inside billing, which violated "a second system must corroborate". Keys are now invoice-style (`inv_<invoice>_a<attempt>`), and a FOOTPRINT assertion requires the public reply to explain the remaining charge as a seat add-on (that reason is only in app_db). The smoke result was discarded.
- **`.env` is loaded from the repo root explicitly** (not `find_dotenv`), so it works from any working directory and from stdin scripts.
- **Context budget for Groq's free tier (starts at 11,000 chars, `max_tokens` 2048).** Groq allows 8,000 tokens per minute per model and rejects any single larger request. Without a budget, later steps of every long trial would become infra errors. The harness elides the *oldest* tool responses first (keeping 300 chars plus a note that the agent can re-request) and never touches the system prompt, ticket, the agent's own messages or the latest response. Both Groq models get the same budget; traces log the full, un-elided responses.
- **Rate-limit waits honour `retry-after` up to 15 minutes, with up to 12 retries.** A free-tier run is throttled, not broken; only waits beyond that cap become `infra_error`.
- **Parallel runs use separate databases** (`TOB_DATABASE_URL` pointing at `tenantops`, `tenantops2`, ...) so one run's reset never clobbers another run's world.
- **The context budget adapts on 413.** The first full runs showed JSON averages about 2 chars/token, and qwen3.8-27b has a 7,000 input-tokens/minute cap, so one trial hit a 413 at 15,000 chars. Now a 413 shrinks the trial's budget by 30% and retries the same step (logged as `context_budget_reduced`); if the latest response alone is too big, its tail is truncated with a note. Only if the context cannot shrink further is it an `infra_error`. Both runs were restarted from scratch under this harness, and the aborted partial runs were discarded.
- **Elided OpenAPI specs become a compact endpoint index, not a stub.** In the second attempt, gpt-oss-120b re-fetched the 9.3K-char app spec 15 times: each new response pushed the spec out of the 11K budget, so the trial measured the budget rather than the model. Now an older spec response is condensed to `METHOD /path ?params body{fields} - summary` lines (app spec 9.3K → 1.9K). The agent still has to discover and fetch specs itself and sees the full spec on first fetch. Runs were restarted again from scratch; the partial runs were discarded.
- **`tob run` resumes an existing run id.** Finished trials in `summary.json` are kept and skipped; infra-error trials are re-run. Long free-tier runs (≈10 h per model) are launched as detached OS processes, so a closed terminal or agent session doesn't lose progress.
- **A run stops cleanly when the provider's daily token quota is exhausted.** Groq's free tier caps each model at 200,000 tokens/day, and a trial uses 30–60K tokens, so that's about 4 trials per model per day. Earlier, every remaining trial failed instantly with a 429 and was recorded as an infra error. Now the run stops after the first daily-quota error, and re-running the same command after the reset resumes it (the interrupted trial is retried).
- **Free-tier runs wait out daily-quota pauses (up to 1 h) instead of stopping.** Groq's TPD window is rolling (`retry-after` was about 20 minutes), so a run on a machine that stays on paces itself across days. Only a `retry-after` over an hour stops the run. A `run.lock` (holding the PID) prevents duplicate copies of a run, and `scripts/resume_runs.ps1` restarts Docker plus both runs in one command after a reboot. User decision (2026-10-13): stay on the free tier with the full 6 × 3 plan and resume daily.
- **Cut to 1 trial per task (user decision, 2026-10-14).** The full 6 × 3 × 2 plan needed 4–5 more days of free-tier quota; the user needed results the same day. Trial 1 of every task runs first anyway (repeat-major order), so the published numbers are trial 1 for all 6 tasks × 2 models. Resuming a run with a smaller `--trials` drops the later-trial records and traces. Without repeats, pass@1 has no standard error; the README says so.
- **Tests run against their own database.** Running `tob validate` during a live run reseeded the run's database mid-trial (gpt-oss-120b `offboard-employee` at step 39). That trial was killed and re-run from scratch. `tests/conftest.py` now switches to `TOB_TEST_DATABASE_URL` when it is set.
